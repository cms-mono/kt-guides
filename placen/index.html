01

서버 환경 — 작년 12월 기준

작년 실행 환경
쿠버네티스 Pod에서 에이전트 실행
  • Ubuntu 22.04 · 메모리 1GB로 시작해 발송 중 4GB로 증설
  • 이번 발송의 실행 환경(물리 서버 · VM · 컨테이너 등)은 아직 정해지지 않았습니다. 아래 사양은 어느 환경이든 동일하게 적용되는 기준으로 보시면 됩니다.
OS
Linux
  • 작년 실적은 Ubuntu 22.04이며, 배포판 제약은 없습니다.
Java
1.8 이상
  • 에이전트 패키지에 JRE 1.8이 함께 들어 있습니다. 별도 설치 없이 동봉된 JRE를 그대로 사용하시면 됩니다.
  • 서버에 다른 버전의 Java가 깔려 있어도, 에이전트는 동봉 JRE를 바라보도록 두는 편이 안전합니다.
메모리
최소 4GB · 권장 8GB
  • 작년 1GB 환경에서 20세션 운용 중 메모리 부족으로 서버가 죽었습니다.
  • 4GB로 올린 뒤 발송은 끝까지 마쳤지만, 사용량이 계속 차오르는 현상은 남아 있었습니다.
  • 그래서 일정 건수마다 정상 재시작해 메모리를 비워주는 방식으로 운영했습니다. 이번에는 처음부터 여유를 두는 편이 낫습니다.
CPU
2코어 이상 · 권장 4코어
  • 20세션을 동시에 돌리는 기준입니다.
디스크
50GB 이상 + 오래된 로그 자동 정리
  • 대량발송 기간에는 log/ 폴더가 빠르게 커집니다.
  • 작년 문제 분석용 파일을 적용했을 때 로그가 급격히 늘어, 서버 부담 때문에 원래 파일로 되돌린 적이 있습니다.
네트워크
발송 대역폭 여유 확보

02

운영 수칙 — 이것만 지키면 됩니다

1세션 20개 유지 설정
  • 처음에는 7세션(세션당 초당 26건, 목표 초당 180건)으로 시작했으나 실제로는 초당 100건에 그쳤습니다.
  • KT 권고로 20세션까지 올렸고, 이후 발송은 이 값으로 끝까지 진행했습니다.
  • 세션을 15개로 줄여봐도 메모리 사용 흐름은 똑같았기 때문에, 처리량을 위해 20개를 유지하는 것이 맞습니다.
  • config.xml의 API_ID / API_PW는 모든 세션에 동일하게 넣습니다.
2프로세스 강제 종료는 가급적 피해 주세요 권고
  • 작년 쿠버네티스 환경에서 메모리 부족으로 서버가 강제 종료되면서 에이전트도 같이 비정상 종료됐습니다.
  • 그 결과 해당 시점의 건들이 '발송중' 상태로 테이블에 그대로 남았습니다.
  • 어떤 환경이든 마찬가지라, 아래 상황은 되도록 피해 주시는 편이 좋습니다.
    • 메모리 부족으로 OS가 프로세스를 강제로 종료하는 상황
    • kill -9 사용
    • 서버 강제 재부팅
  • 평상시 종료는 stopAgent.sh를 이용한 정상 종료를 권장드립니다.
  • 다만 정말 급한 상황에서는 부득이하게 강제 종료가 필요할 수 있습니다. 그때는 종료한 시각을 기록해 두시면 이후 남은 건을 확인하고 정리하기가 훨씬 수월합니다.
3야간에도 에이전트를 내리지 말 것 필수
  • 이동통신사 발송 결과는 최대 24시간까지 뒤늦게 들어옵니다.
  • 에이전트를 내리면 그 결과를 받을 주체가 없어져, 실제로는 발송됐는데 상태값이 갱신되지 않습니다.
  • 야간 발송 중단은 종료가 아니라 발송 제한(PAUSE) 설정으로 처리합니다. <PAUSE>
      <START_TIME>1800</START_TIME>
      <END_TIME>1000</END_TIME>
    </PAUSE>
  • 위 설정이면 18시부터 다음 날 10시까지 새로 보내는 동작만 멈추고, 결과 수신과 상태 점검은 계속 돌아갑니다.
  • 따라서 야간에 로그가 계속 쌓이는 것은 정상입니다. 발송이 되고 있다는 뜻이 아닙니다.
  • config.xml을 고치면 에이전트를 다시 시작해야 반영됩니다.
4템플릿은 전부 미리 등록·검수 완료 사전
  • 사용할 템플릿은 하나도 빠짐없이 발송 전에 등록과 검수가 끝나 있어야 합니다.
  • 검수에 3일가량 걸릴 수 있으므로, 문구 확정 일정을 그만큼 앞당겨 잡아야 합니다.
  • 작년에는 발송이 시작된 뒤에도 문구가 바뀌어 긴급 검수를 네 차례 요청했습니다.
5적재 시점과 SCHEDULE_TIME 설정
  • 에이전트는 SCHEDULE_TIME을 <database><limit> 값(시간 단위)과 비교해, 너무 오래된 건은 스스로 실패 처리합니다.
  • 이 값은 기본 24시간으로 설정되어 있습니다. 즉 SCHEDULE_TIME이 24시간을 넘긴 건은 발송되지 않고 실패 처리됩니다.
  • 작년에 금요일에 넣어둔 50만 건을 월요일에 돌렸다가 전량이 이 규칙에 걸려, 알림톡을 건너뛰고 문자로 나간 사고가 있었습니다.
  • 미리 데이터를 넣어두는 방식으로 운영한다면 둘 중 하나로 맞춰야 합니다.
    • limit 값을 넉넉하게 잡아두거나
    • 발송 직전에 SCHEDULE_TIME을 현재 시각으로 갱신
6결과 데이터는 발송 후 7일 안에 마감 사전
  • 커뮤니즈의 발송 결과 보관 기간이 7일입니다. 그 이후에는 결과 조회로 다시 받아올 방법이 없습니다.
  • 발송 기간 중 매일 M2X_SUBMIT에 남아 있는 건수(STATUS 1 · 4)를 확인해 주세요.
  • 발송 종료 후 7일 안에 결과 확인을 끝내는 일정으로 잡아야 합니다.

  • 메모리 1GB 환경에서 20세션 운용이 원인
  • 메모리 4GB로 증설
  • 100만 건 단위로 정상 재시작하며 운영
